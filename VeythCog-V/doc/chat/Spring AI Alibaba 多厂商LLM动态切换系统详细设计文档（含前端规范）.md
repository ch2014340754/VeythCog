# Spring AI Alibaba 多厂商LLM动态切换系统详细设计文档（含前端规范）

## 1\. 文档概述

### 1\.1 设计目标

基于 Spring AI Alibaba 框架，实现**阿里通义、Deepseek 双大模型厂商动态切换**能力，支持运行时动态切换模型、独立厂商密钥管理、统一对话记忆治理。同时定义**前端标准化交互规范**，保证前后端对接统一、简洁、可扩展。彻底解决多厂商Controller冗余、对话记忆混乱、多端适配混乱问题。

### 1\.2 适用范围

后端AI对话服务、流式对话服务、模型动态路由服务、对话记忆管理服务；前端AI对话页面、模型切换交互、会话管理交互。暂定支持厂商：阿里DashScope、Deepseek。

### 1\.3 核心解决问题

- 摒弃多厂商多Controller冗余架构，统一后端接口入口

- 各厂商独立 AK、Endpoint、模型参数配置，完全隔离

- 对话记忆与LLM厂商解耦，统一存储、统一组装、统一截断

- 支持运行时动态切换模型/厂商，无需重启服务

- 统一前端交互规范，避免前端多厂商适配、记忆错乱、兼容问题

- 架构可扩展，后续可无缝新增其他AI厂商

## 2\. 整体架构设计

### 2\.1 架构核心思想

**后端：统一入口 \+ 路由分发 \+ 工厂创建 \+ 独立记忆 \+ 动态缓存**

**前端：统一对话页面 \+ 全局模型切换 \+ 会话绑定策略 \+ 无厂商差异化渲染**

核心原则：**前后端均不对厂商做差异化业务逻辑，厂商差异完全收敛在后端工厂适配层**。

### 2\.2 整体请求链路

前端选择模型 \-\> 携带厂商/模型参数请求统一接口 \-\> 统一AI Controller \-\> 对话记忆服务组装上下文 \-\> LLM动态路由 \-\> 厂商模型工厂 \-\> 对应LLM服务 \-\> 统一格式结果返回前端渲染

### 2\.3 架构分层说明

|分层|职责|核心特性|
|---|---|---|
|前端交互层|模型选择、会话管理、消息渲染、流式展示、参数透传|一套页面适配所有厂商，无差异化代码|
|后端接口层|统一接收对话、流式对话请求；参数校验、鉴权、统一封装返回结果|全局唯一Controller，无厂商代码冗余|
|记忆服务层|对话历史存储、消息组装、上下文截断、会话管理|完全解耦厂商，全局唯一逻辑|
|路由服务层|根据厂商、模型编码路由对应模型实例；参数适配、异常兜底|动态分发，运行时切换无感知|
|工厂适配层|各厂商独立ChatModel创建、AK/Endpoint绑定、厂商参数适配|收敛所有厂商差异，可扩展|
|缓存层|缓存各厂商模型实例，避免频繁创建销毁|提升接口性能，支持动态刷新配置|

## 3\. 后端核心功能详细设计

### 3\.1 厂商与模型配置设计（核心）

所有厂商、模型、密钥配置**不硬编码、不写yaml静态配置**，统一数据库存储，支持后台动态配置、热生效。

#### 3\.1\.1 数据库配置表（llm\_vendor\_config）

核心字段：

- vendor：厂商标识（固定值：dashscope / deepseek）

- model\_code：模型编码（如qwen\-max、qwen\-plus、deepseek\-chat）

- model\_name：模型展示名称

- api\_key：厂商独立密钥（每个模型/厂商可独立配置）

- endpoint：厂商私有地址（为空则使用官方默认）

- max\_context\_tokens：模型最大上下文窗口（用于记忆截断）

- temperature：默认温度

- status：启用/禁用状态

### 3\.2 模型工厂设计

采用**接口\+多实现工厂模式**，收敛所有厂商SDK差异。

- DashScopeChatModelFactory：适配阿里通义系列模型

- DeepseekChatModelFactory：基于OpenAI协议适配Deepseek模型

每个模型实例独立绑定AK、Endpoint，完全隔离密钥，无串号风险。

### 3\.3 模型路由与缓存设计

内存缓存Key：`vendor:model_code`，懒加载创建模型实例，支持动态刷新配置、清空缓存热更新。

### 3\.4 对话记忆系统设计

记忆层完全与厂商解耦，统一基于 Spring AI Message 模型组装上下文。

- 存储：Redis（活跃会话）\+ MySQL（持久化）

- 自适应截断：根据不同模型的 max\_context\_tokens 自动截断历史消息

- 支持两种会话模式：会话绑定模型（推荐）、同会话自由切换模型

### 3\.5 后端统一接口

对外仅暴露一套接口，区分普通对话、SSE流式对话，无厂商区分。

## 4\. 前端详细设计（新增完整章节）

### 4\.1 前端核心设计原则

**前端不感知任何厂商差异、不区分接口、不做格式适配，只负责「模型选择 \+ 参数透传 \+ 统一渲染」**。

所有厂商适配、密钥、上下文处理、模型差异全部由后端兜底。

### 4\.2 前端所需实现功能范围

无需改造现有对话核心逻辑，仅新增少量配套能力：

- 模型下拉选择器（全局/对话页）

- 动态拉取后端可用模型列表（不硬编码）

- 会话与模型绑定逻辑控制

- 请求统一透传 vendor、modelCode 参数

- 会话列表展示当前模型名称

- 异常状态、禁用状态交互处理

### 4\.3 模型列表获取规范

前端启动/进入对话页时，调用后端接口获取**所有启用的模型列表**，动态渲染下拉选项。

后端返回字段：

- vendor：厂商标识

- modelCode：模型唯一编码

- modelName：前端展示名称

- status：启用/禁用

优势：后端新增、下线模型、新增厂商，前端**零代码改动**。

### 4\.4 模型切换交互策略（正式环境推荐方案）

**采用：会话创建时绑定模型，会话内禁止切换（生产最优方案）**

#### 4\.4\.1 交互规则

- 新建会话：下拉框可选择模型，创建会话后该会话永久绑定当前 vendor \+ modelCode

- 进入已有会话：模型下拉框**置灰不可编辑**

- 用户如需切换模型：必须新建对话

#### 4\.4\.2 优势

- 彻底规避「同会话多模型画风混乱」的用户体验问题

- 记忆上下文稳定，无技术风险、无体验瑕疵

- 业内主流AI平台统一方案

### 4\.5 备选策略（测试/内部环境）

**自由切换模式：同会话随时可切换模型**

- 下拉框全程可编辑

- 切换时前端弹窗轻提示：`已切换模型，下一轮提问将使用新模型回答，上下文将继续复用`

- 仅用于调试、对比模型效果，不对外用户开放

### 4\.6 请求参数规范（强制统一）

前端所有对话请求（同步 \+ SSE 流式）必须携带以下三个核心参数：

```Plain Text
{
  "conversationId": "会话唯一ID",
  "vendor": "dashscope / deepseek",
  "modelCode": "qwen-max / deepseek-chat / ...",
  "content": "用户提问内容"
}
```

原有对话逻辑、流式接收、消息拼接、页面渲染**完全无需改动**。

### 4\.7 会话列表展示规范

每条会话卡片需要展示：**会话名称 \+ 绑定模型名称**，让用户清晰区分不同模型会话。

### 4\.8 前端边界条件处理

- 后端模型禁用：前端下拉选项置灰不可选

- LLM 超时/限流/异常：前端统一错误提示，不需要区分厂商

- 网络中断：原有重试逻辑不变

- 流式输出：只做文本拼接，不处理任何厂商差异化字段

### 4\.9 前端禁止事项（重要）

- ❌ 禁止前端写死厂商、模型列表

- ❌ 禁止前端区分不同后端接口地址

- ❌ 禁止前端对不同厂商做差异化渲染逻辑

- ❌ 禁止前端处理上下文截断、token 计算、密钥相关逻辑

## 5\. 关键技术实现细节

### 5\.1 阿里DashScope模型适配

基于 Spring AI Alibaba 原生 DashScopeChatModel 实现，工厂类动态读取数据库AK、模型名、参数，构建独立实例。

### 5\.2 Deepseek模型适配

Deepseek 完全兼容 OpenAI API 协议，基于 Spring AI 原生 OpenAiChatModel 适配，自定义Endpoint、绑定Deepseek AK。

### 5\.3 多AK隔离保障

所有ChatModel实例均为运行时动态新建，每个实例绑定独立的apiKey和endpoint，无全局公共密钥，彻底避免配置混淆。

### 5\.4 流式对话记忆处理

服务端等待完整响应结束后统一存入记忆，前端只负责流式拼接展示，保证所有厂商消息格式统一。

## 6\. 扩展性设计

### 6\.1 新增厂商扩展

后端：新增数据库配置 \+ 新增工厂实现类，核心代码无改动。

前端：**零改动**，自动适配新厂商模型。

### 6\.2 动态配置扩展

支持Nacos热更新、模型动态上下线，前端无需发布即可生效。

## 7\. 风险与解决方案

|风险点|解决方案|
|---|---|
|多模型上下文窗口不一致报错|后端记忆层统一动态截断|
|多厂商AK混淆、泄露|AK加密落库，实例级独立绑定|
|模型实例过多内存占用高|懒加载缓存、闲置回收、手动刷新缓存|
|跨厂商对话体验割裂|生产环境会话绑定固定模型，禁止中途切换|
|前端适配繁琐、多端不一致|统一前端规范，厂商差异全部后端收敛|

## 8\. 前后端联调总结

1. **前端改动极小**：仅新增模型下拉选择、参数透传、会话绑定控制，核心对话逻辑完全复用
